## 1. Write the behavior and risk contract first

Document:

- user-visible behavior and default state;
- consent and disable behavior;
- lifecycle entry points;
- local data read/written and retention;
- network hosts, methods and payload fields;
- whether credentials, session, viewer ID or evidence can leave the device;
- account/server mutations and rollback limits;
- pacing, caps, retries, timeouts and failure behavior;
- minimum SDK and dependency changes;
- runtime conditions static analysis cannot prove.

If any material choice is unresolved, stop before implementation.

For this inline account-action UI, preserve exactly one visible post-Share Block control. It always opens one compact `Block and report` modal containing bounded identity, the immutable post excerpt, a report-reason selector, a persisted `Also block this profile` checkbox, one dynamic `Block`/`Report` positive action, concise disclosure, and Cancel. The explicit positive-action tap always durably queues exactly one report; when the checkbox is enabled it also submits the immutable target through the shared Block scheduler. It must not contain a dedicated Report action, a second editor/review modal, notes, a consent checkbox, outbox controls, `Safe processing`, or `Before exact review`. There is no one-click bypass.

Any revision to reporting must preserve the combined modal's explicit positive tap as the sole report-creation authority; binding to the initiating Activity, viewer, and unchanged foreground-owner generation; required non-empty username, canonical 4–24 digit ID, non-empty Unicode-safe 280-UTF-16-unit excerpt, and selected reason; optional Threads permalinks that reject user-info, non-default ports, query, and fragment; concise in-modal disclosure plus complete Settings disclosure that the backend stores full connection IP, full HTTP User-Agent, and derived city/country with operator visibility/correlation, backup inclusion, and no automatic server expiry before administrative deletion; complete local-retention/cancel-race disclosure; stable pseudonym with no raw viewer/session/cookie/token data; the patchlet-070-owned exact endpoint class; a viewer-scoped SQLite schema with separately owned database/schema/table/index tokens, 1,000 pending/500 history/16 KiB UTF-8 bounds, integrity checks and atomic pre-network enqueue/attempt reservation; one distinct durable outbox row for every accepted modal action; foreground-only retry/review state; and success only after 2xx plus complete valid-UTF-8 strict duplicate-free JSON with one boolean `ok: true`. A new host, field, automatic trigger, schema migration, or retention promise requires explicit authorization and policy review.

## 2. Choose the stable/version-specific split

Put ordinary Android logic in reviewable Java under a feature-owned asset tree. Add it to `ModBootstrap` or a deterministically generated feature registry rather than inserting another direct activity hook.

Put every obfuscated/private Threads call in a minimal exact-SHA host rewrite or rendered Smali template. It must use named bindings from an APK-SHA-bound resolution. Do not place an obfuscated descriptor directly in stable feature source.

For the shared inline row, patchlet 060's exact-SHA host-class helper is the sole inline/Report owner of media lookup, author lookup, author-ID and username resolution. It creates one immutable `InlineBlockRequest.createHostBound` snapshot containing the media key, numeric target, bounded label, and native author/media models only as opaque `Object` values. Stable inline/Report code must not reacquire those raw seams or call the private already-blocked predicate. Patchlet 070 may extract code/caption/permalink only from the captured opaque media model, trying the code-derived canonical URL before the strict permalink fallback. The sole reviewed mod-namespace author-ID call remains patchlet 030's callback-free `ThreadsBlockBridge.prepareModel`; do not add another mod caller, reflective substitute, or field shortcut. Stable code must not persist either object or trust it as identity. Durable manual enqueue, running-state persistence and attempt persistence must precede bridge consumption; manual work must not reserve or read passive pacing. The SHA-bound bridge must cast the author hint, re-read its canonical ID and require exact target equality. A null/missing/expired/account-or-session-mismatched hint must use the reviewed cache-first session get-or-create-by-ID bridge path, and passive work must not consume inline hints. Every returned model must pass the same target-ID equality check; the old profile-fetch callback and `lookup_failure` terminal must remain absent. Preserve narrow failure ownership: direct-ID and resolved-row casts/cache calls stay in separate bounded regions and dispatch outside try; model-ID and already-blocked private calls live only in callback-free bridge preparation; result interpretation stays outside try; and preparation/mutation invokes are protected separately. Every mod callback remains outside protected ranges. Every bridge result and native started/failure/success outcome must enter stable `BridgeCallbackDispatcher` and cross checked `Handler.post` into `Delivery.run`, with zero real callbacks elsewhere; downstream mod code then runs after both the scheduler bridge-call catch and private host stack unwind and cannot be caught as a bridge- or mutation-seam failure.

The automatic/manual scheduler ownership handoff must pass literal true before a sole `Throwable` catch containing only reviewed bridge selection, argument loads, and entry invokes, a false result must return before that catch, and no alternate control-flow edge may enter it. Its outside handler must route fixed `bridge_exception` to the exact failure owner. Their six `BridgeCallback` methods consume `Delivery.run` directly and must retain reviewed started/status, failure, completion-save, save-exception-to-quarantine, quarantine-before-release, success, and normal/exceptional release effects that are CFG-reachable and post-dominate their applicable accepted subpaths; decorative or unreviewed early-return-bypassable calls do not count. Every asserted call argument must come from a live CFG-dominating field/constant/result/allocation definition on the applicable path, with both words of a wide value protected from clobber; a skipped lexical decoy cannot prove a token, Handler, delay, Runnable, target, status, or callback. Model all covering try handlers as exceptional successors and reject ordinary branches into reviewed handler tails. From the accepted automatic-current and manual-completion-CAS branches, reject any return, catch-return, or backward cycle before the exact completion save. `BlockRun` must own one immutable target only, with no target list, cursor, loop, or `next()` call. Automatic success derives the pacing delay and releases through the shared scheduler; only a new manual-first scheduler token may select another visible target.

New Block failure stages must be fixed literals owned by the private adapter or stable scheduler and added to patchlet 020's closed `BlockDiagnostic` map in the same revision. The formatter may accept only the stage token plus fixed context booleans; it must not accept or copy identifiers, usernames, URLs, payloads, host objects, server responses, or `Throwable` text. Unknown stages map to a fixed unknown code without echo. Preserve the 120-character detail, 240-character Activity/alert status, and 200-character log bounds, `mirror=n/a`, `bridge=r6`, one viewer-scoped alert per persisted failure, and distinct pre-dispatch/mutation stage semantics. `model_id_exception` / `CB-BRG-112` and `already_blocked_exception` / `CB-BRG-113` are fixed current contracts and must not be collapsed into a mismatch, success, or generic mutation failure.

Preserve terminal ownership across UI and scheduler layers. Every inline failure before durable enqueue must record one closed diagnostic before its UI callback; once queued, only the scheduler records terminal state. Passive reservation failure must record history, one alert, status and bounded log output and must not call the bridge. If native success is confirmed but completion persistence fails, install the bounded process-local viewer/target latch before attempting the strict `completion_review_threads_<viewerId>` set; reject it at selection and pre-dispatch, create no backoff/passive queue/automatic retry, and pause passive work on corrupt, oversized, full, exceptional, or uncommitted quarantine state. Treat private Compose/layout placement as a version-sensitive seam even when the rendered control is stable Java. Prove the host hierarchy, parent/container closes, sibling ordering, object/register liveness, and next branch. Exactly one host snapshot result and one Block control must occur after Share's container closes; patchlet 070 must consume that request and must not render a second Report sibling, icon, or `threadsmod_inline_report` tag. The exact-SHA resolution must also prove the native Kotlin default-mask semantics for the modifier parameter, and raw signed DEX must prove that the decorated test-tag/visibility modifier reaches the button call with that bit clear; a defaulted or clobbered modifier fails closed. A control intended to sit beside a native action must not be injected inside that action's container. In-app navigation targets must remain non-exported and have no intent filter unless a separately reviewed public surface is explicitly required.

Passive blocking is not a generic permission to scan or batch the signed list. Patchlet 020 owns one atomically replaced indexed generation, exact 600,000 ms foreground refresh cadence, background lookup worker, durable passive admission, and the shared scheduler. The fetch path may verify and atomically index only; it must never enumerate a generation into Block work. A still-visible match enters durable passive state only after self/completion/duplicate/quarantine checks. Before each reservation the shared scheduler must recheck foreground viewer, visibility, database generation and ID membership, quarantine, current limits, and manual-queue priority. ## 3. Add declarative metadata

Create `features/<ordered-id>/patchlet.json` and `PATCHLET.md`.

The metadata must declare dependencies, resolution requirements, risks, canonical inputs, bounded operations, preconditions, postconditions, release gates, AI policy, and exact ownership of class families/descriptors, rewrite rules, manifest components, host hooks, preference keys, and local database schemas. Add the patchlet to `catalog.json` in dependency order. Ownership must not overlap another patchlet.

Operations must use supported deterministic types. Do not add an arbitrary command runner to bypass the operation schema.

## 4. Define symbol roles and evidence

For each new private seam, define the semantic role before selecting a descriptor. Candidate extraction should use stable evidence such as manifest ownership, descriptor shapes, known route/analytics strings, caller/callee relationships and callback behavior.

Create a bounded AI task only when deterministic rules leave multiple candidates. AI may select candidates; it may not implement the adapter or edit production files.

Account mutation, authenticated session access, the exact-host author/media snapshot and sole mod author-ID ownership, Compose/private UI seams, register allocation, and callback terminal semantics require human review on every new APK digest.

For native menu integration, define roles for the item-list owner, stable item key, insertion boundary, row renderer, modifier, click interface, and destination contract. A future version must fail closed if any one of those roles or proofs is unresolved.

## 5. Make application idempotent

Every rewrite must declare an exact path, complete before/after state and expected count. Every generated class set or rendered template must have a deterministic content hash.

Partial presence is a conflict. Applying the patchlet twice must change nothing on the second pass.

## 7. Extend release preservation rules

Declare exactly which APK entries the new feature may change. Unrelated native libraries, assets and DEX files must remain byte-identical. A generated asset exclusion must be an exact resolution-owned file, never a directory or glob, with a human-reviewed reason and a blocking replacement integrity gate. Any private bridge change must also update and pass the resolution-bound signed-Dex bridge-flow contract, verifier fixtures, source/fixture hashes, catalog/schema checks, and release integration; a source/template or decompiler-only check is insufficient. Any release-tool invocation change must preserve the AST-proven exact named-parameter contract against the parsed callee rather than relying on a literal ban. If a signed-evidence count or semantic expectation is duplicated between the release wrapper and its positive fixture harness, patchlet 090 must parse both scripts, find exactly one literal comparison in each, prove that the reviewed literals are identical, and report `publicationOrdering.releaseToolEvidenceCompatibility: true`; duplicate, missing, nonliteral, or divergent expectations fail closed.
