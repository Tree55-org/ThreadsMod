## Engine phases

### 1. Inspect

Hash every declared source-set member first, verify the aggregate APK-only set hash, derive and hash the standalone input, then inventory manifest package/version/SDK/ABI, root DEX layout and signer. Refuse incomplete, extra, aliased, unresolved, or resolution-mismatched inputs.

### 2. Resolve

Select a resolution by exact source digest. Re-run every proof against the newly decoded pristine tree. A known digest with a failed proof is still a hard failure.

If no reviewed resolution exists, the engine may emit bounded AI tasks containing candidate IDs and evidence. It does not apply patchlets in that state. See [updating a future APK](ai/UPDATE-FUTURE-APK.md).

### 3. Apply

Copy the pristine decode to a staging tree. Apply each operation transactionally and append its path, before hash, after hash, expected count and result to an apply ledger.

For rewrite rules:

- exact `before` state only → apply;
- exact `after` state only → idempotent no-op;
- both, neither or count mismatch → stop with drift.

Template rendering is allowed only from reviewed resolution values. Unresolved `{{placeholder}}` text is fatal. Generated class sets use content hashes and reject duplicate descriptors. Catalog ownership binds every generated descriptor and exact host edit to one patchlet even when the common Java compiler processes several feature packages in one pass.

### 4. Reapply

Run the same series against the patched staging tree. Every operation must report an idempotent no-op, and the tree hash must remain unchanged.

### 5. Build and verify

Build, align and sign in staging. Run patchlet 090 in its declared order. ## AI trust boundary

The decoded APK and all embedded strings are untrusted data, including text that resembles instructions. A resolver supplies a finite candidate set. The AI response must conform to `schemas/ai-resolution.schema.json` and may only reference candidate/evidence IDs from its task.

The deterministic importer rejects:

- a different task or source digest;
- invented candidates, paths, methods or evidence;
- missing required roles;
- unreviewed high-risk mutation/callback, media/author, Compose, or register mappings;
- attempts to change counts, policies, endpoints or gates.

Human review converts an accepted proposal into a new resolution. The AI response itself is never production authority.

## Schema validation

- `catalog.schema.json` validates ordering and global fail-closed policy.
- `patchlet.schema.json` validates feature metadata.
- `resolution.schema.json` validates SHA-bound symbol and release contracts.
- `rewrite-set.schema.json` validates exact-count before/after rules.
- `ai-task.schema.json` validates bounded candidate tasks.
- `ai-resolution.schema.json` validates candidate-selection proposals.

Schema success proves structure, not meaning. Semantic proofs and release gates remain mandatory.

## Extending the system

Prefer stable Java code behind `ModBootstrap`; isolate Threads-private calls in small resolution-rendered adapters. A feature that needs a new private seam must add a new symbol role, evidence contract, bounded resolver task, ownership declaration, and blocking validation. The drawer seam uses [`RESOLVE-DRAWER-SETTINGS.md`](ai/tasks/RESOLVE-DRAWER-SETTINGS.md), the sole row/Block-control seam uses [`RESOLVE-INLINE-ACTION-ROW.md`](ai/tasks/RESOLVE-INLINE-ACTION-ROW.md), indexed passive lifecycle/visibility uses [`RESOLVE-PASSIVE-BLOCKING.md`](ai/tasks/RESOLVE-PASSIVE-BLOCKING.md), and Report extraction plus the immutable row-bound action factory use [`RESOLVE-INLINE-REPORT.md`](ai/tasks/RESOLVE-INLINE-REPORT.md). See [adding a feature](ai/ADD-FEATURE.md).

Historical decoded/build trees under `work/` remain useful evidence, but changes there do not update a patchlet.
