## One-modal action contract

Every control tap opens exactly one compact modal; there is no one-click bypass. It contains:

- title **Block and report**;
- bounded username/profile ID identity;
- the immutable Unicode-safe post excerpt supplied by patchlet 070;
- one report-reason selector;
- the persisted **Also block this profile** checkbox owned by patchlet 050;
- a concise report/privacy disclosure;
- one dynamic positive action and Cancel.

The positive label is **Block** when the checkbox is checked and **Report** when it is unchecked. Either label represents the same report authority: one explicit tap always submits the immutable request and selected reason to patchlet 070's durable queue. When checked, the same tap also sends the immutable numeric target through the shared Block scheduler. When unchecked, no Block work is created. Each checkbox change is synchronously committed so the next modal and a restarted app use the same value.

The modal must not contain or launch a dedicated Report button, `ReportDialog`, `InlineReportClick`, editor, `Review report` action, exact-payload preview, consent checkbox, note field, outbox controls, or second modal. It does not perform network I/O directly. The removed `Safe processing` and `Before exact review` sections and all one-click paths remain forbidden.

The report queue and optional Block scheduler are separate execution results after the single user action. Report persistence is handled by patchlet 070. Optional manual Block still follows the viewer-scoped single-flight scheduler, durable attempt persistence, backoff, quarantine, and `ThreadsBlockBridge`, but it is not subject to the passive delay pair or retired capacity limits; this patchlet never invokes Threads' private mutation helper. Queued or started Block is not success. Only its native success callback may produce the green check and any Block-success dismissal animation. Report-only completion clears the local confirming state without pretending that a native Block occurred.

## Scheduler and model boundary

For optional Block, the controller first durably enqueues the viewer-scoped manual request. Only after that commit may the scheduler stage the opaque row model in its bounded viewer/target/session registry; it marks work running and persists the attempt before consuming the hint. Manual inline work is intentionally unpaced and uncapped. The bridge re-reads the private model ID and requires equality with the immutable request target. A missing, expired, account/session-mismatched, or null hint leaves the numeric target, so eligible work uses patchlet 030's cache-first session get-or-create-by-ID path. A null or unusable placeholder fails as `placeholder_model_invalid`; the retired profile-fetch callback and `lookup_failure` path stay absent.

The normalized username is bounded local presentation and manual queue/history metadata. It never replaces the numeric target, enters the bridge model registry, selects an automatic target, or authorizes mutation. The opaque models are in-process execution hints and are never persisted.

Every terminal failure before durable Block queue ownership is recorded exactly once through the closed identifier-free `BlockDiagnostic` owner before the UI failure callback. Once `onQueued` fires, terminal Block persistence is scheduler-owned and the click adapter remains UI-only, preventing duplicate alerts.

The separate inline-hook counters are diagnostic visibility, not mutation or report authority. Exactly one hook count records host entry, request-unavailable records only a factory/admission absence, render records control construction, and adapter-exception records the fixed catch stage. They are bounded and identifier-free and must not replace the normal closed Block failure diagnostic.
