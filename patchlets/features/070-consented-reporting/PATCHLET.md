# 070 — Combined-modal report backend and row request factory

Revision 10 adds the second and final reviewed write path: one activation-statistics ping per installed build to `/v1/installs` on the same already-reviewed AWS host. It exists so activations and a coarse device mix can be counted without a third-party analytics SDK, a new host, or any account identity. `InstallStatsPayload` is a closed 13-field object with a fixed key order whose text values are restricted to one safe token charset, so the serialized form never needs escaping and a hostile device string cannot inject structure. `InstallStats` derives the install identifier as an HMAC of a local random secret over the fixed tag `install:v1`, with no account, advertising or hardware input, so it is neither the reporting pseudonym nor linkable to a Threads account. It sends at most once per version code and mod build, on the first eligible foreground resume, on one bounded daemon thread, and every failure is silent and simply leaves the ping due again on a later foreground resume. The host harness proves the exact key set, strict escape-free serialization, fail-closed validation of every required field, and the absence of every account, target and free-text field. Through the 020 r22 series the opening dialog and Settings disclosed the ping and its exact contents; since 020 r23 deleted that dialog, the Settings screen's Reports card is the sole disclosure surface. The `/v1/installs` route must exist on the relay before any ping is accepted; this revision ships only the client. Revision 10 shipped behind patchlet 020's opt-in gate. Patchlet 020 r21 removed that gate, so from the 2026-09-05 revision-59 Release the ping is unconditional on the first eligible foreground resume of every installation; through the 020 r22 series it was disclosed in the first-run notice rather than gated, and since 020 r23 deleted that notice it is disclosed in the Settings screen's Reports card; the closed 13-key payload, HMAC install identifier, at-most-one-per-installed-build rule and never-affects-other-work guarantee are unchanged.

## Immutable row request

Patchlet 060's exact-SHA host helper owns media lookup, displayed-author lookup, author-ID, username, and opaque author/media capture. Patchlet 070's resolution owns only the captured media descriptor, caption object/text chain, primary code accessor, and fallback permalink accessor used by its factory. The factory reads all three from that same captured media instance, never performs another media or author lookup, and supplies one canonical URL and excerpt to the row-bound request constructor. For Threads 444, the primary code call is the reviewed `Media.A75()` accessor and the fallback permalink call is `Media.A7o()`; the latter is consulted only after the code candidate fails stable validation. Stable Java receives a non-empty normalized username, canonical 4–24 digit profile ID, non-empty Unicode-safe excerpt capped at 280 UTF-16 units without a dangling surrogate, the same local item key used by the Block request, and a validated canonical permalink. A cleaned empty caption is represented exactly as `(no text in this post)`. Obfuscated descriptors remain only in rendered Smali. The local item key binds the row but is never transmitted.

For a new explicit action, permalink validation is mandatory. The primary captured code is accepted only as the bounded ASCII shortcode alphabet of letters, digits, `_`, and `-`, then combined with the immutable normalized username. Fallback URL input is accepted only from the exact reviewed HTTPS hosts `www.threads.com` or `www.threads.net`, with no user-info, explicit port, query, fragment, percent-encoding, trailing segment, or path outside `/@<normalized-username>/post/<shortcode>`. The path username must equal the immutable request username. Both routes emit only `https://www.threads.com/@<username>/post/<shortcode>`.

The factory returns data, not authority: it cannot queue, send, render a control, launch UI, or decide current-viewer/self eligibility during composition. Queue authority exists only at the explicit positive-action tap in patchlet 060's combined modal. The queue call must be bound to that initiating foreground Activity and its live viewer, reject self-targets or changed context, validate the selected reason, and preserve the immutable request. No lifecycle callback, automatic list work, Block callback, retry callback, Settings action, or background worker may create another report.

## Single-step durable queue

The positive action always requests one durable report enqueue, regardless of the modal's **Also block this profile** value. The checkbox controls only patchlet 060's optional Block scheduler path. Reporting does not wait for native Block success and Block does not replace report persistence.

Payload preparation runs off the main thread. It derives the stable per-install/account pseudonym and normalized language/time-zone metadata, validates the immutable target, excerpt, and selected reason, performs a full fail-closed storage preflight, commits the candidate pseudonym, and durably enqueues the exact payload before starting delivery. The callback reports the local queue result; it never claims server acceptance. Foreground/account replacement before the durable commit fails closed. Once a report is durably queued, later delivery is viewer-scoped and remains foreground-only.

The wire body contains `pseudonym`, `platform=threads`, numeric `targetId`, normalized `targetUser`, bounded optional `targetName`, the canonical post permalink as `targetUrl` and the identical sole `evidence[0]`, selected reason, an empty bounded note value for protocol compatibility, the required excerpt as `quote`, language, and time zone. `postId`, raw viewer ID, local item key, Threads session, cookies, tokens, and authorization headers never enter the payload. A process-wide cookie handler makes transport fail closed.

The mandatory-link rule applies at new request enqueue, not while decoding durable state. Existing outbox/history payloads from an earlier revision may have an empty `targetUrl` with an empty `evidence` array and remain readable, reviewable, retryable, or deletable under the legacy validation path. No database column or schema revision is added: SQLite stays at v2 with the existing fail-closed v1-to-v2 migration. A newly created request cannot use that compatibility path.

The combined modal gives the concise disclosure required for the explicit action: the report is queued and delivery can expose the stable pseudonym, language/time zone, server-visible IP and User-Agent, possible coarse location, and server-operator access. Patchlet 050's private Settings/Activity surfaces retain the fuller server/local retention, outbox/history, retry, cancellation-race, and deletion explanation. Cancellation before the positive tap creates nothing; after enqueue, local cancellation can race active delivery and cannot recall a server-accepted report.

## Delivery and storage contract

Reports are committed to the viewer-scoped outbox before transport. Delivery is foreground-only and single-flight. Every attempt is durably reserved before POST; redirects are refused; request and response bodies are bounded. Success requires a 2xx response plus complete valid-UTF-8 strict JSON whose unique `ok` member is the JSON Boolean `true`. Duplicate or escape-equivalent names, malformed encoding, lenient syntax, trailing data, and string `"true"` are failures.

HTTP 403 is terminal. Transient failures retry after 30 seconds, 1 minute, 2 minutes, 5 minutes, 15 minutes, 1 hour, 6 hours, and then 12-hour intervals. After 15 attempts the outcome is `gave_up`: acknowledgement is unconfirmed even though the server may have accepted a POST. Exact wakes run only for the same foreground viewer. Interruption or account replacement retains explicit viewer-scoped state.

The SQLite v2 outbox is capped at 1,000 pending rows per viewer, each payload is at most 16 KiB UTF-8, and history is capped at 500 rows per viewer. Every explicit row action receives its own primary-key report identity; v2 removes the old `UNIQUE(viewer_key,target_key)` constraint so target-level pending deduplication cannot silently discard a later post/excerpt from the same profile. The due/history indexes and history's viewer/report identity constraint remain.

The only accepted upgrade is exact v1 to v2. One fail-closed transaction validates the v1 table, index, history, and `quick_check` shape, copies every outbox row and verifies the count, swaps the outbox, and recreates the due index. Any unexpected version, shape, integrity result, copy/count mismatch, or DDL failure rolls back without resetting user data. Enqueue, attempt reservation, cancellation, retry, and terminal transitions remain transactional. A foreground-generation Snapshot preflight validates the complete viewer scope before reservation or POST, rejects self-target rows and cross-table report-ID collisions, and propagates corrupt/wrong-type pseudonym state even when tables are empty. Malformed, oversized, schema-drifted, or corrupt storage is never reset or overwritten; it blocks delivery for review.

The private Activity may inspect, retry, or delete unsent payloads for the live viewer. Cancellation fails while delivery is active. Terminal history trimming occurs only with a verified app-owned insertion, stored times must be plausible, and long waits use overflow-safe bounded wake chunks.
