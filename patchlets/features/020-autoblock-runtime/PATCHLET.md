# 020 — Indexed passive blocking runtime

Revision 24 (2026-09-06) moves list refresh from the whole-file signed `blocklist.json` to the chunked v3 index the backend has published since 2026-09-06, so the client scales to millions of records and downloads only what changed. The compiled read allowlist is now three fixed bases (GitHub raw, jsDelivr, the AWS relay, in that order); the signed root is `<base>blocklist/v3/manifest.json` and objects are `<base>blocklist/v3/objects/<name>`, where `CloneBlockerEndpoints.objectUrl` admits only 64 lowercase hex characters plus `.json` or `.ndjson.gz` before any URL text exists. `parseAndVerify` keeps the envelope, Ed25519, `updatedAt`, +24 h clock, 30-day stale and rollback checks verbatim and then validates the root type-strictly (`v` 3, `hash` `sha256-hi32`, `maxChunkRows` and `maxChunkBytes` within the compiled caps, `platforms.threads` with `k`, `g`, `total` and exactly `1 << g` 64-hex group names); the whole-file target loop, `MAX_TARGETS` and the `idNames`/`profiles` fallbacks are gone. Two new classes own the objects: `ObjectFetcher` GETs one object with the same connection discipline as the root fetch plus a mandatory `Accept-Encoding: identity`, bounds it by the caller's cap and the signed byte count, proves `SHA-256(bytes)` against the name before returning, and retries a mirror once only after an `IOException`; `ChunkInstaller` reuses committed group tables whose sha is unchanged, parses each fetched group table strictly with `JsonReader`, marks every bucket whose chunk sha differs (or every bucket when the bucket bits changed or no valid generation exists), and stages each replaced chunk one at a time through a capped `GZIPInputStream` and a strict per-line `JsonReader` into `blocklist_staging`. A chunk is rejected whole for a non-object line, a malformed `i`, an id row without a valid `u`, a duplicate id or conflicting normalized username within the chunk, a row whose `sha256("threads:" + i)` (or `sha256("threads:@" + u)` for a handle-only row) does not fall in the chunk's bucket, or a row or byte count that differs from the signed group entry; handle-only rows are counted toward the signed total but never indexed, so `Records:` reports installed threads id rows (1,607 of the 1,633 rows in the 2026-09-06 fixture). `BlocklistStore` is schema v3: `blocklist_targets` gains an `h32` column and index, the username index becomes UNIQUE on `username_key`, `blocklist_metadata` widens its counts to 16,777,216 and records `bucket_bits`, and `blocklist_chunks`, `blocklist_groups` and `blocklist_staging` are new; `replaceVerified(Context, InstallPlan, ...)` measures each replaced bucket's exact new-id set difference against the still-complete previous generation, deletes each replaced bucket's hash range, copies the staged chunk in with `INSERT ... SELECT`, records the chunk and group names, and commits generation + 1 with `target_count` = the sum of installed id rows; `snapshot` and `markFetchedUnchanged` no longer run the row-count proof on every call (the Activity polls every second); `requireRowCount` now runs only inside `replaceVerified` (against the previous generation before replacement and against the installed rows after it) and inside the reviewed migrations. Revision 16 hardens the revision-15 passive store and refresh boundaries without changing the exact ten-minute cadence, indexed one-target scheduler, endpoints, or mutation path. Every invalid indexed lookup now carries the generation actually observed. Unknown-generation faults and faults observed against the current committed generation latch passive work paused; suppression is permitted only when the invalid result names a known generation strictly older than the latest committed verified generation. Thus a missing or unknown observation can never be mistaken for a stale result, while a genuinely older in-flight fault cannot re-latch after a newer verified commit clears the prior pause. Raw `list_refresh_not_before` reads are exception-safe as well as exact-`Long` typed: any read exception, wrong type, overflow, or implausible value pauses ordinary refresh fail closed rather than granting an early retry.

Revision 16 also makes signed-list row acceptance all-or-nothing. A non-object target, malformed or noncanonical platform field, or malformed Threads row rejects the complete payload and preserves the prior verified generation. Only a structurally valid canonical non-Threads row is excluded from the Threads index. Canonical and fixture evidence must distinguish that exclusion from malformed-row tolerance; no invalid Threads ID, username, platform, or row shape may be silently ignored.

Revision 15 makes one scheduler drain own at most one independently selected visible target. The background selector copies no page-sized visible-ID collection and performs one indexed lookup; `BlockRun` owns one immutable numeric ID and has no target list, cursor, loop, or `next()` continuation. On confirmed success it releases the scheduler with the current pace deadline, and only a new manual-first drain may select another current visible match. A stale selected match is removed and re-selection occurs through one bounded delayed drain rather than a synchronous scan. ## Passive-delay contract

The Settings UI may atomically replace one complete validated passive-delay snapshot. The scheduler reads it at each passive selection/reservation boundary so a change takes effect before another eligible passive attempt. A completely absent snapshot uses the 4–10 second defaults; a partial, mistyped, fractional, out-of-range, step-invalid, internally inconsistent, corrupt, or uncertain snapshot pauses passive work fail closed. Manual inline work never reads this pair as rate or pacing authority. If the atomic save commit fails, rollback restores every Android SharedPreferences value type that could have occupied either delay key—including corrupt Boolean, Long, Float, String, and StringSet values—so failed persistence cannot erase evidence and manufacture valid missing-key defaults.

`BlockLimitsHarness` executes the passive minimum, maximum, defaults, ordering rule, every accepted whole-second step, and deliberately fractional rejected values. `BlockLimitsStoreHarness` executes the production `BlockLimitsStore` against a fake that reproduces Android's process-local map change on a failed `commit()`. It proves one-editor/one-commit atomic success; exact rollback of Integer, String, Boolean, Long, Float, StringSet, and missing-key snapshots; rejection without rewrite of every partial or invalid Integer snapshot; fail-closed preference-read exceptions; and absence of retired capacity admission. If both the validated write and rollback commits fail, a process uncertainty latch remains set even when replacement values are visible in memory. A later failed write plus successful rollback cannot clear pre-existing uncertainty; only a successful complete validated write can. Structural gates separately prove the two-field model/store contract, checked stored-value route, uncertainty latch, viewer-derived history/deadline/status keys, every timed scheduler wait's wake before return, acceptance checks for every scheduler-critical Handler enqueue, manual unpaced routing, and atomic attempt-plus-passive-deadline persistence before passive bridge dispatch.

The active viewer used by Activity/Settings and reporting is not restored from preferences. Only `AutoBlockSync.onResume` may publish a viewer after extracting a canonical ID from the live foreground Threads session, and it publishes that ID only in process memory. The retired `ui_active_viewer` key remains cataloged solely so upgraded installs can remove it; production code never writes or reads its value. If that cleanup cannot commit, account actions pause. A mod Activity recreated after process death therefore has no report or manual-work scope until the signed-in feed is re-entered in the new process.

| Control | Allowed values | Default |
|---|---:|---:|
| Passive-block minimum delay | 2–60 seconds, exact whole seconds | 4 seconds |
| Passive-block maximum delay | 3–60 seconds, exact whole seconds and not below minimum | 10 seconds |

`BlockLimits` and `BlockLimitsStore`, the two live passive-delay keys, deletion-only retired `limit_*` keys, the durable `list_refresh_not_before` deadline, passive pace/backoff times, attempt history, manual queue, runtime status, history, and alert keys are owned only by this patchlet. Attempt history remains observation and diagnostic data, not capacity authority. Patchlet 050 displays and edits the delay pair but does not own its runtime or storage contract.

## Database v3 and Current status

The verified-list database metadata binds the active generation, verified timestamp text and epoch, fetch time, total record count (installed threads id rows), bucket bits, and exact new-target count. Rows live in `blocklist_targets` keyed by numeric id with a stored `h32` bucket hash (indexed) and a UNIQUE normalized-username index; `blocklist_chunks` and `blocklist_groups` record the committed chunk and group names per bucket so the next refresh downloads only chunks whose name changed, and `blocklist_staging` holds hash-proven chunks until one transaction replaces their buckets. Atomic replacement computes new targets by incoming numeric-ID set difference, per replaced bucket, against the immediately previous committed generation inside the same transaction and before that bucket's rows are removed; net row-count change is not an acceptable substitute. The reviewed v1-to-v2 migration preserves the existing generation and marks only that retained pre-feature generation with `new_target_count=-1`; the reviewed v2-to-v3 migration moves the retained generation into the v3 tables with its counts and timestamps intact and `bucket_bits` 0, so the first v3 refresh replaces every bucket and counts only ids not already present. A first verified install stores its full id-row count as new. A verified 304, or a root that is not strictly newer, changes fetch metadata and stores zero new rows without changing target membership or generation.

## Stable safety contract

- Always enabled. `isEnabled` returns true for any non-null context and reads no preference, `disable(Context)` does not exist, there is no opt-in switch and no in-app way to turn passive work off, and the mod Settings screen's Passive blocking card discloses the behaviour instead of gating it; since revision 23 there is no first-run notice and the clone opens with no mod dialog.
- Signed Ed25519 payload required before an atomic indexed generation is used.
- Numeric Threads IDs are the sole mutation authority; indexed usernames are metadata only. Duplicate normalized usernames and stored/visible username conflicts reject the candidate rather than changing identity authority.
- Every refresh attempt installs an exact 600,000 ms not-before guard before it starts and persists it across pause/resume and process recreation; on completion the worker re-installs it by 600,000 ms after success or by the next 15/30/60/120/300 s ladder step after failure (five steps per foreground session, then 600,000 ms; the ladder resets on success and on each new foreground session). Worker-start rejection re-advances from rejection time. A resume with no valid index starts one attempt immediately; forced refresh is the only other bypass, and neither can erase or transfer another viewer's deadline.
- Verified timestamp text and its epoch-millisecond field must rebind exactly both before replacement and whenever stored metadata is read.
- Valid match, valid non-match, and invalid/unavailable/corrupt store are distinct. Invalid store state pauses passive work until a strictly newer committed verified generation clears the latch; an older in-flight invalid result cannot re-latch afterward.
- Refresh never enumerates signed-list rows into Block work; only a current clipped-viewport observation plus background exact-ID match may admit a target.
- Visibility/work authority grants are main-thread-only. Off-main pause/update/unregister may only revoke existing authority and must serialize through `PASSIVE_ADMISSION_LOCK`.
- Foreground gate, the validated passive-only randomized delay pair, failure backoff, and watchdog; manual inline work has no passive pacing or capacity cap.
- Every scheduler-critical Handler enqueue checks Android's boolean acceptance result; rejection releases passive ownership or records a bounded durable-work pause. Only optional toast delivery is best effort.
- Stop on opaque native failure and fail closed on persistence failure.
- Automatic, retry, and inline requests share one serialized scheduler; only passive work reserves a pacing deadline.
- Every attempt is durably persisted before its native mutation bridge call. A passive reservation atomically persists the selected next-admission deadline with its attempt before dispatch, and later paths cannot clear or shorten it.
- The callback-free exact-SHA passive preflight runs before passive-running state and passive delay/attempt reservation. A native already-blocked result reserves no delay or attempt and submits no mutation; completion-save uncertainty quarantines it.
- Attempt-reservation failure is persisted through the closed diagnostic owner before any retry wake; no native request is sent.
- Confirmed native success followed by local completion-save failure installs viewer/target quarantine before scheduler release, never schedules automatic mutation retry, and reports whether durable or process-local fail-closed review state is active.
- A missing terminal callback or rejected watchdog enqueue after bridge dispatch installs the same target review quarantine. Automatic work gets no backoff/retry path; inline work is marked abandoned until an explicit atomic retry.
- Corrupt/oversized completion-review state pauses automatic work; explicit manual Retry/Retry all removes only matching quarantine entries atomically with the queue transition.
- A live inline author-model hint is staged only after durable queue commit and consumed only after running-state and attempt persistence; it is never persisted or used by automatic work.
- Hintless and automatic work uses the reviewed cache-first, session get-or-create-by-ID bridge path; a null/wrong-ID placeholder fails closed before mutation.
- Block failures use only the closed identifier-free `BlockDiagnostic` map; dynamic identifiers, URLs, host exceptions, and unknown stage text are never copied into Activity status, alerts, history detail, or logs.
- Bridge and native callback adapters contain no direct mod-callback invoke; the stable dispatcher enqueues every result and does not catch the real callback, while the scheduler's callback consumers run directly from `Delivery.run` without an unchecked repost. Their signed-Dex bodies must retain the reviewed started/status, exact failure route, completion-save, quarantine-before-release, success dispatch, and continuation effects rather than merely retain the interface methods.
- Automatic and manual scheduler ownership handoff occurs with a literal true argument before a single-entry bridge-selection/argument-load/invocation-only `Throwable` try range, and the false result returns before that range. Its sole outside handler uses the fixed `bridge_exception` literal and exact automatic `handleFailure` or manual `fail` route; no fail/finish/dispatch callback or scheduler-state call can be caught and relabeled.
- Callback effects must be CFG-reachable and post-dominate their applicable accepted subpath, not be decorative later instructions or bypassable by an unreviewed early terminal. Every asserted callback/caller argument must have a live CFG-dominating reaching definition on the applicable path, with the complete scalar or wide register value unwritten before its call; a nearer dead field, constant, token, Handler, delay, or Runnable definition is not evidence. All-path checks conservatively include every covering try handler and forbid normal entry into the reviewed terminal catch tail. The accepted automatic `isCurrent` branch cannot return, throw into a catch-return, or enter a backward cycle before `markDone`, and the accepted manual completion-CAS branch has the same obligation before `markManualBlocked`. A thrown completion save converges with false on quarantine before release, and manual success retains both normal and exceptional `finally` release paths.
- Automatic success has no same-owner target continuation. It releases through the checked shared drain wake, which honors the already-persisted passive deadline, re-enters manual selection first, and creates a new scheduler token before another passive target can be selected.
- `BlockRun` may own only one `String targetId`. A `List<String>` target field, visible-ID temporary collection, index/`while`/`List.get` iteration, or `next()` method/call is a release-gate failure.
- After passive preflight, the scheduler rechecks foreground/viewer, manual priority, passive-delay and completion state, visibility, generation, exact-ID/username membership, and store validity, then repeats complete current authority immediately before passive-running persistence, passive delay/attempt reservation, and bridge dispatch.
- Pre-reservation exits create no pacing deadline. Once passive delay/attempt reservation commits, no authority loss, manual preemption, scheduler handoff failure, bridge throw, or uncertain mutation may roll back, clear, or shorten its viewer-scoped deadline.
- User-confirmed inline work is selected before more automatic work; active queue entries are never reset or evicted.
- Backoff and passive-delay waits wake explicitly and check enqueue acceptance, interrupted or callback-uncertain inline work becomes abandoned for review, and enabled passive work resumes after the manual queue drains only when no quarantine pauses it.
- Activity/account replacement releases to the current viewer, while bounded per-viewer forced-refresh requests cannot clobber each other.
- Restored private Activities cannot recover an active account from disk; a live session hook must re-establish the in-process viewer.
- No Threads session, credential or viewer ID is supplied to list GETs.
- Background or automatic scheduler work never creates a report. Only the combined modal's explicit positive action may call patchlet 070; when its persisted checkbox is enabled, the independent Block portion enters this scheduler through the ordinary manual queue.
