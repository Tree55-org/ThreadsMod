## Activity contract

The Activity page attaches its visible scroll/root shell before it reads preferences or constructs dynamic cards. It puts the current failure/status alert first, followed by the dedicated list-fetch, record-count, new-record, and database-index lines, blocking summaries, and bounded queue/history controls. If corrupt legacy state prevents rendering, the attached shell is replaced with an explicit fail-closed review card and stored data is not reset. Stat cards never clear their own layout parameters; `addStatRow` supplies explicit non-null weighted parent parameters.

Activity also shows the active viewer's report outbox/review state and permits foreground retry or explicit deletion of a still-pending payload. That viewer must have been validated from the live Threads session in this process; Activity/Settings restoration from Recents after process death exposes no account scope until the user re-enters a signed-in feed. Deletion requires confirmation, cannot remove an active delivery, cannot recall a report already accepted by the server, and creates no false server-deletion claim. Corrupt, oversized, or wrong-type report storage remains unchanged for review rather than being reset.

## Settings contract

The Settings page presents Passive blocking as a static `Always on.` description with no switch, the same current database/refresh/index summary and explicit sync, navigation to Activity, the **Also block this profile** default, and one atomic two-field passive-delay form. Minimum accepts 2–60 seconds and maximum 3–60 seconds, both in exact whole-second steps, with defaults 4 and 10 seconds and maximum not below minimum. Manual inline actions are deliberately unpaced and uncapped. A sync verifies and indexes the list; it does not select or queue every listed target.

Current status uses explicit compact lines rather than the generic scheduler message: **List fetch** shows waiting, fetching, verifying, indexing, complete, unchanged, retained failure, or unavailable; **Records** shows the committed indexed total; **New this refresh** shows the exact committed incoming-ID set difference or **Unavailable**; and **Database index** shows ready/indexing/missing/review plus generation. While a replacement is indexing, the previous generation remains active. A failed refresh says the previous index was retained when true and never presents corrupt storage as an empty successful database.

`ui_also_block_profile` defaults to checked so the original Block-oriented control continues to include Block until the user changes it. Both the Settings switch and every checkbox change inside patchlet 060's modal synchronously commit this same Boolean. Its committed value is therefore the next modal's default after dismissal and after app restart. The modal still opens on every inline tap so the user can inspect the reason and excerpt and explicitly submit the report. There is no one-click bypass, and the retired one-click/dismiss preferences are not owned by this revision.

The full report disclosure names the canonical post permalink alongside the profile username, numeric profile ID, bounded excerpt, selected reason, stable pseudonym, language, and time zone. It explains that the permalink is queued locally and, on delivery, appears identically in `targetUrl` and the sole `evidence` entry. Patchlet 050 does not derive or validate that link; patchlet 070 owns the SHA-bound captured-media seam, canonicalization, new-queue validation, and legacy-outbox compatibility.

The release gate extracts `buildContent`, `saveLimits`, and `parseSeconds` after removing comments, then proves exactly the two labeled passive-delay fields map in order and whole-second steps to one `BlockLimits.checked` call before atomic persistence, with no retired control. If write or rollback durability cannot be confirmed, the message says passive blocking is paused until a later complete valid save rather than claiming nothing changed.

Both activities are `android:exported="false"` and have no intent filter. They are reachable only from in-app mod UI; this patchlet does not create a second launcher or public deep link.

The compact **Configure proxy** card remains after the visible Settings shell is attached. It launches only patchlet 080's non-exported `ProxySettingsActivity` after an explicit tap. It does not read credentials, request VPN consent, or start or stop network transport during Activity construction.
